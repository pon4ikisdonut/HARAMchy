# PROMPT ДЛЯ OPENCODE: сборка дистрибутива "HARAMchy" с нуля (LFS-based)

Ты — автономный инженерный агент внутри opencode CLI, запущенного на Windows (с доступом к консоли/PowerShell
и к WSL2). Твоя задача — с нуля (Linux From Scratch style, БЕЗ archiso/debootstrap/live-build, без
наследования от Debian/Arch/Ubuntu) собрать полноценный загружаемый x86_64 Linux-дистрибутив
**HARAMchy** — задуманный как "халяльный ответ omarchy": работает и на реальном железе (generic
ATA/NVMe/USB/virtio drivers, GRUB с UEFI+BIOS fallback), и в VMware для тестов.

Работаешь в режиме автопилота: не спрашивай подтверждения на каждый шаг, но ОБЯЗАТЕЛЬНО делай `git commit`
после каждой значимой стадии (toolchain, base system, kernel, DE, панический модуль, финальный ISO) и
пуш в уже существующий репозиторий **https://github.com/pon4ikisdonut/HARAMchy** (репо создано, публичное,
с автоинициализированным README — сделай `git clone`/добавь remote `origin` и работай через обычный
`git push` из Windows-окружения, где у пользователя уже настроен git с учётными данными; не пытайся
создавать репозиторий заново и не используй `gh repo create`).

Настрой permission-правила так: деструктивные операции с реальными дисками (`dd` на физическое устройство,
`mkfs`/`wipefs` на не-loopback устройство, любая запись на диск C:) требуют ручного подтверждения (`ask`);
всё остальное (bash, edit, read, glob, grep, webfetch, git) — автоапрув.

## 0. Окружение

- Хост: Windows + WSL2 (`Ubuntu-22.04`, дефолтный дистрибутив). Все build-шаги LFS (toolchain, chroot,
  компиляция ядра) выполняй ВНУТРИ WSL через `wsl.exe -d Ubuntu-22.04 -- bash -lc "..."`, так как LFS
  требует Linux-хост. Git commit/push можно делать как из WSL, так и напрямую из Windows-консоли — важно
  только, чтобы итоговый remote указывал на `https://github.com/pon4ikisdonut/HARAMchy`.
- Рабочая директория: диск **E:**, никогда не пиши временные/итоговые файлы на C: (там нет места).
  Внутри WSL это путь `/mnt/e/haramchy`. Структура:
  ```
  E:\haramchy\
    src/            # исходники всех пакетов (tarball'ы, кэш)
    lfs-root/       # $LFS — корень собираемой системы
    build/          # scratch-директории сборки, точки монтирования
    kernel-src/     # исходники ядра + патчи (haram-panic модуль)
    haram-rules/    # база правил "харам", парсер, конфиги
    hyprland-dots/  # рандомные dotfiles, стянутые из интернета
    iso/            # финальный образ
    docs/           # заметки, README, changelog
  ```
- Перед началом проверь: `wsl --status`, свободное место на E: (`fsutil volume diskfree E:`), доступность
  вложенной виртуализации, если планируешь гонять QEMU внутри WSL2 (иначе финальный тест — только через
  VMware Workstation на хосте, ISO просто лежит на E:).
- Веди `docs/PROGRESS.md` с чек-листом стадий и `docs/DECISIONS.md` с обоснованием любых отступлений от
  плана.

## 1. Базовая система — Linux From Scratch, без чужого бренда

1. Следуй методологии LFS (актуальная стабильная версия, systemd-вариант книги): temporary toolchain
   (binutils, gcc, glibc) в chroot, затем полная сборка базовой системы (coreutils, bash, systemd,
   базовые библиотеки).
2. НЕ используй debootstrap/pacstrap/archiso/live-build — всё компилируется из исходников. Каждый пакет
   собирай через воспроизводимый build-script в `docs/build-scripts/<pkg>.sh`.
3. `/etc/os-release`, баннеры, `uname`-related строки — везде `HARAMchy`, никаких упоминаний
   Debian/Ubuntu/Arch/LFS/omarchy в user-facing местах системы (в README можно упоминать методологию и
   то, что проект задуман как "халяльный ответ omarchy").

## 2. Ядро — с патчем "харам-детектора" и кастомной паникой

Собери ядро с нуля из vanilla-исходников (последняя стабильная LTS-ветка), конфигурация — generic
x86_64 desktop (virtio_*, ahci, nvme, usb-storage, xhci, e1000/virtio-net и т.п. — грузится и в VMware, и
на реальном железе).

Реализуй кастомный модуль/подсистему `haram_guard`:

1. **Слой обнаружения** (LSM-хук/character device + netlink интерфейс в ядре): хук на syscalls
   открытия/записи файлов, exec; получает события от userspace-демона `haramd` (см. п.3). Модуль
   экспортирует `/proc/haram/report` — запись туда с кодом нарушения запускает пайплайн наказания.
2. **Пайплайн наказания** (весь текст локализуется по `$LANG`/`/etc/locale.conf`, минимум RU и EN, с
   fallback на EN):
   - Шаг A: остановить обычный вывод, вывести на весь экран (framebuffer console, `printk` KERN_EMERG +
     прямой доступ к vt) текст "ОБНАРУЖЕН ХАРАМ!! СРОЧНОЕ САМОУНИЧТОЖЕНИЕ!!!" (RU) /
     "HARAM DETECTED!! EMERGENCY SELF-DESTRUCT!!!" (EN).
   - Шаг B: 10-секундный обратный отчёт крупными цифрами на экране, синхронно — сирена воздушной тревоги:
     попробовать проиграть заранее подготовленный `.wav`-файл сирены через `aplay` (если ALSA/устройство
     звука доступно на момент паники); если `aplay` недоступен/падает/не успевает инициализироваться —
     фоллбек на PC speaker (`KIOCSOUND` ioctl на `/dev/console`, модулированная частота вверх-вниз раз в
     ~1 сек, имитация воющей сирены). Реализуй это как shell/C-хелпер `haram-siren`, который сам решает,
     какой путь использовать, с таймаутом на попытку `aplay` (~0.5 сек), чтобы не тормозить отчёт.
   - Шаг C: по достижении 0 — `panic("ОБНАРУЖЕН ХАРАМ!!")` (или локализованный эквивалент).
   - Заложи debug-лазейку: запись "СМИЛОСТИВЬСЯ"/"MERCY" в `/proc/haram/abort` в первые 3 секунды отменяет
     пайплайн — иначе невозможно тестировать.
3. **Кейс "свинья/pig"**: любое совпадение слова (регистронезависимо, транслит, базовый leetspeak) в
   (a) вводе в shell (перехват через `haramd`, слушающий pty), (b) содержимом создаваемых/редактируемых
   файлов, (c) имени процесса/аргументах — немедленно триггерит полный пайплайн из п.2.

## 3. Демон `haramd` + база правил Корана (strict + heuristic)

Детект-логику вынеси в системный демон `haramd` (C или Rust, без runtime-зависимостей типа Python),
который слушает pty-сессии, `inotify` на ключевые пути, hook на новые процессы, и держит правила в
`haram-rules/rules.yaml` со структурой: `id`, `category` (вероучение/ширк, еда и напитки, азартные игры и
алкоголь, убийство/насилие/имущество, прелюбодеяние и мораль, ложь и клевета, социальные нормы,
изображения идолов), `severity`, `detection_type` (`keyword`, `process_name`, `file_content_regex`,
`syscall_pattern`, `filetype_heuristic`), `patterns` (regex/слова на нескольких языках), `quran_reference`,
`enforcement` (`strict` или `heuristic`).

- **Strict** (реально роняет систему): слово "свинья"/pig и вариации, запуск бинарника с именем
  `alcohol`/`vodka`/`casino`/`poker`, попытка установить пакет из харам-категории через пакетный менеджер,
  попытка `install food` через дневное время Рамадана (если включено в `haram-rules/config.toml`).
- **Heuristic** (эвристическая модель, не всегда 100% точная, но включена и активно используется, а не
  просто заглушка): для распознавания "изображений идолов/реалистичных портретов людей" — прогоняй
  создаваемые/скачиваемые файлы (`.jpg/.png/.webp/.mp4`) через легковесную offline CV-модель (например,
  простой face-detection через OpenCV Haar cascades или аналог, без интернет-запросов в runtime); при
  срабатывании — тот же пайплайн паники, но с явной пометкой в логе `enforcement: heuristic` и
  вероятностью совпадения. Так же эвристически (по именам файлов/пакетов/тегам) детектируй
  гадательные/оккультные приложения, ростовщические/скам-финансовые сервисы и т.п. — там, где строгая
  проверка невозможна.
- Namaz/Рамадан: вычисляй время намаза локально (астрономические формулы или захардкоженная таблица по
  таймзоне из конфига, без интернета в runtime).

Раздели прозрачно strict/heuristic и задокументируй в `docs/RULES_COVERAGE.md` — что реально железно
проверяется, а что символически/эвристически.

## 4. DE — Hyprland с рандомными dotfiles

- Собери Hyprland и минимальный Wayland-стек с нуля (wlroots, xdg-desktop-portal и т.п., версии
  зафиксируй в `docs/DEPS.md`).
- Найди через `webfetch` пару популярных публичных репозиториев с Hyprland-dotfiles, выбери один (или
  смешай несколько), склонируй в `hyprland-dots/`, замени упоминания оригинального автора/дистрибутива в
  комментариях на нейтральные, подключи как дефолтный конфиг нового пользователя.

## 5. Пакетный менеджер — "уебищный", свой, не Debian

- Собственный минималистичный пакетный менеджер (bash+tar+plain-text/SQLite база установленных пакетов),
  CLI типа `hrm install <pkg>` / `hrm remove` / `hrm update` — внешне топорный клон apt по духу
  (тормозной, с лишним выводом, странными предупреждениями), но без упоминаний Debian/dpkg/apt и без
  реального `.deb` формата — свой формат `.hrm` (tar.gz + манифест).
- Интеграция с `haramd`: попытка поставить пакет из харам-категории по имени/тегам в манифесте триггерит
  пайплайн паники до завершения установки.

## 6. Финальная стадия — сборка ISO и тест

1. Собери загрузочный ISO (свой initramfs, GRUB, kernel, rootfs) через `xorriso`/`grub-mkrescue`, файл —
   `E:\haramchy\iso\haramchy-<date>.iso`.
2. Протестируй загрузку (QEMU внутри WSL2 при наличии вложенной виртуализации, иначе — инструкция для
   VMware Workstation): boot до Hyprland-сессии, ручная проверка strict-правила (слово "свинья" в
   терминале → отчёт 10 сек + сирена (aplay/pcspkr) + панике с нужным текстом).
3. Запиши `docs/HOWTO_TEST.md`: настройки VM (BIOS/UEFI, RAM, диск), как безопасно тестировать панику
   (снапшот VM перед тестом).

## 8. Общие правила поведения агента

- Работай стадиями, обновляя `docs/PROGRESS.md` чек-боксами после каждой.
- Если что-то технически невозможно (версия пакета не собирается, эвристика ненадёжна) — не молчи и не
  притворяйся; фиксируй в `docs/DECISIONS.md` и выбирай рабочую альтернативу.
- Никогда не пиши временные/build-файлы на диск C: — весь объём работы только на E:.
- Перед любой операцией записи на нецикличное блочное устройство — остановись и спроси подтверждение;
  это единственный обязательный чекпоинт.
- В конце — `docs/SUMMARY.md`: что собрано, что работает строго, что эвристически, как запустить тест,
  что осталось доделать руками.
